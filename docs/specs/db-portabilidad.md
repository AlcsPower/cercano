## 1. Alcance

| Incluye | No incluye |
|---|---|
| Motores SQLite, PostgreSQL y SQL Server (este último condicionado a F8-01) | Alta disponibilidad, réplicas, varios nodos de API |
| Respaldo firmado, verificación, restauración | Migración sin corte de servicio |
| Migración asistida con corte y rollback | Cifrado de la BD o del archivo dentro de la aplicación |
| Auditoría `db.*` | Migrar los binarios de adjuntos a otra ubicación |

## 2. Compatibilidad de esquema

### 2.1 Tipos por motor

| Concepto | SQLite | PostgreSQL | SQL Server |
|---|---|---|---|
| Identificadores, texto | `TEXT` | `TEXT` | `NVARCHAR(MAX)` / `NVARCHAR(n)` donde haya límite |
| Marcas de tiempo | `TEXT` | `TEXT` | `NVARCHAR(33)` |
| Booleanos | `INTEGER` 0/1 | `SMALLINT` 0/1 | `BIT` |
| Contadores | `INTEGER` | `BIGINT` | `BIGINT` |
| Clave primaria autoincremental | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `BIGINT IDENTITY(1,1)` |
| Índice único parcial | soportado | soportado | soportado con índice filtrado |

Se evitan `BOOLEAN` nativo y tipos de fecha nativos a propósito: el formato de tiempo es el mismo en los tres motores y la comparación lexicográfica se mantiene.

### 2.2 Tiempo

- Formato único **`YYYY-MM-DDTHH:MM:SS.sssZ`** (RFC 3339, UTC, milisegundos), generado en Rust.
- Las comparaciones son de cadena (`ts < ?`, `last_seen_at > ?`); con ancho fijo y UTC son correctas.
- La ventana de gracia de dispositivos deja de usar `strftime` y se calcula en Rust.
- **`audit_events.ts` no se reescribe nunca**: forma parte del hash de cada evento. Los valores legados de otras tablas se normalizan con una migración de datos idempotente y auditada.

### 2.3 Autoincremento y claves

- `login_attempts.id` y `mfa_challenges.id` son contadores por motor. La lectura del identificador insertado se encapsula en `db-core` (`lastval` de PostgreSQL, `SCOPE_IDENTITY()` de SQL Server, `last_insert_rowid` de SQLite).
- Todos los demás identificadores son UUID generados en Rust; ninguna consulta depende de la sintaxis de identidad.

### 2.4 Upsert

Tres plantillas en `db-core`, una por dialecto: `ON CONFLICT … DO UPDATE` (SQLite/PostgreSQL) y `UPDATE … IF @@ROWCOUNT = 0 INSERT` (SQL Server; se evita `MERGE` por sus problemas conocidos). Las consultas que las usan no escriben el fragmento a mano.

### 2.5 Inmutabilidad de auditoría

| Motor | Mecanismo |
|---|---|
| SQLite | `BEFORE UPDATE`/`BEFORE DELETE … RAISE(ABORT, …)` (actual) |
| PostgreSQL | `BEFORE UPDATE OR DELETE … EXECUTE FUNCTION` con `RAISE EXCEPTION` |
| SQL Server | `INSTEAD OF UPDATE, DELETE … THROW` |

Semántica idéntica: la sentencia falla, la fila no cambia y el error llega al llamador. Además se revocan los permisos de `UPDATE`/`DELETE` sobre `audit_events` al usuario de la aplicación cuando el motor lo permite (defensa en profundidad).

### 2.6 Migraciones

- Un archivo por motor y versión: `migrations/<sqlite|postgres|mssql>/NNN_nombre.sql`, embebido con `include_str!`.
- `schema_migrations(version, name, applied_at)` existe en los tres motores; las migraciones se aplican en orden, en transacción, y una falla detiene el arranque (comportamiento actual).
- **Fingerprint**: tras migrar, se introspecciona el esquema (columnas, tipos normalizados, índices, claves) y se calcula un SHA-256. El valor esperado por motor vive en `control-plane/db-core/tests/schema_fingerprint.json` y CI falla si cambia sin actualizar el archivo en el mismo PR.

## 3. Formato de archivo `cercano-backup` v1

### 3.1 Contenedor

Un solo archivo gzip, sin tar:

```
cercano-backup-20261110T182000Z.jsonl.gz
  línea 1        manifiesto (JSON canónico RFC 8785, una sola línea)
  líneas 2..n    una fila por línea: {"table":"<tabla>","row":{…}}
```

- Orden: tablas en el orden declarado en el manifiesto; filas por clave primaria ascendente. El orden es determinista para que dos respaldos de un mismo estado sean comparables.
- Escritura a `<nombre>.tmp` y `rename` atómico; un `.tmp` residual indica fallo y no se ofrece en la lista.

### 3.2 Manifiesto

| Campo | Tipo | Obligatorio | Descripción |
|---|---|:---:|---|
| `format` | entero | sí | `1`. Un archivo con formato mayor se rechaza. |
| `engine` | `sqlite` \| `postgres` \| `mssql` | sí | Motor de origen. |
| `engine_version` | string | sí | Versión reportada por el motor. |
| `schema_version` | entero | sí | Última versión aplicada en `schema_migrations`. |
| `created_at` | string | sí | RFC 3339 con milisegundos, UTC. |
| `app_version` | string | sí | Versión de `cercano-api`. |
| `tables` | array | sí | `[{ "name", "rows", "sha256" }]` en el orden de escritura. |
| `attachments` | objeto | sí | `{ "included": bool, "archive": string? , "count": n, "total_bytes": n, "sha256": string? }`. |
| `archive_sha256` | string | sí | SHA-256 del contenido (ver §3.3). |
| `key_id` | string | sí | Identificador de la clave de firma (`audit_signing_key`). |
| `signature` | string | sí | Ed25519 en hex sobre los 32 bytes de `archive_sha256`. |

### 3.3 Hash y firma

```
preimagen = manifiesto_canónico_sin(archive_sha256, signature) || "\n"
            || línea_2 || "\n" || … || línea_n || "\n"
archive_sha256 = SHA-256(preimagen)
signature      = Ed25519_sign(audit_signing_key, "cercano-backup-v1\0" || archive_sha256_bytes)
sha256(tabla)  = SHA-256(concat(canonical_json(fila) para cada fila de la tabla))
```

La verificación recalcula la preimagen en streaming (sin cargar el archivo en memoria), comprueba `archive_sha256`, la firma, y luego el hash de cada tabla. Cualquier discrepancia indica tabla y número de fila.

### 3.4 Contenido

Se incluyen las 21 tablas actuales: `users`, `sessions`, `login_attempts`, `devices`, `user_permissions`, `system_info`, `schema_migrations`, `mfa_challenges`, `revoked_roles`, `build_jobs`, `audit_events`, `audit_checkpoints`, `audit_export_checkpoint`, `chat_devices`, `chat_device_sessions`, `chat_auth_nonces`, `chat_conversations`, `chat_messages`, `chat_reads`, `chat_attachments`, `chat_branding`. Una tabla nueva debe añadirse a la lista en la misma tarea que la crea (prueba de CI: toda tabla de `schema_migrations` aparece en el manifiesto).

**No se incluye**: `id_ed25519`, `id_ed25519.pub`, `audit_signing_key`, artefactos de build ni los binarios de adjuntos (van en su archivo compañero, §3.5).

### 3.5 Adjuntos

Cuando `attachments.included = true`, el mismo trabajo produce `cercano-attachments-<misma-marca>.tar.gz` con el árbol `chat-attachments/`, y el manifiesto guarda su `sha256`. La restauración conjunta valida ambos; si falta el compañero, restaura la BD y avisa de que los adjuntos quedaron fuera. No se empaquetan adjuntos `.tmp` ni huérfanos.

### 3.6 Verificación

Pasos, en orden, sin escribir nada:

1. Descomprimir en streaming y validar que la línea 1 es un manifiesto `format: 1`.
2. Recalcular `archive_sha256` y verificar la firma (con el prefijo de dominio `cercano-backup-v1\0`) con la clave pública de `audit_signing_key`. El prefijo impide que una firma de respaldo se reutilice como firma de checkpoint.
3. Validar que `schema_version` no es mayor que la soportada por el binario.
4. Recalcular el hash de cada tabla y comparar con el manifiesto.
5. Comprobar que el conjunto de tablas del manifiesto coincide con el esquema del binario.

Cualquier fallo aborta con un código de la tabla §4.4 y **no modifica** la base.

### 3.7 Evolución del formato

- Campos nuevos: opcionales y aditivos; `format` no cambia.
- Cambio incompatible: `format` sube y el binario anterior rechaza el archivo con un mensaje explícito.
- Un `schema_version` mayor que el soportado se rechaza antes de leer datos; nunca se aplica un respaldo «hacia atrás» adivinando columnas.

## 4. API

### 4.1 Permisos y reautenticación

- Todas las rutas exigen `db:admin`, que **solo** tiene el rol `admin`; `operator` y `auditor` reciben `403`.
- Crear respaldo, descargar y listar: sesión válida.
- **Restaurar y migrar** exigen además reautenticación: `POST /api/db/reauth` con la contraseña y, si la cuenta tiene 2FA activo, un `totp_code` válido, devuelve un token de 60 s, ligado a la sesión y a la IP, que va en `X-DB-Reauth`. Sin él, `403 db.reauth_required`.
- Toda operación deja evento `db.*` (§6). Los datos del archivo nunca se registran.

### 4.2 Endpoints

| Método | Ruta | Cuerpo / parámetros | Respuesta |
|---|---|---|---|
| GET | `/api/db/status` | — | Motor, versión, ruta o host, tamaño, `schema_version`, último respaldo, modo mantenimiento, migración en curso |
| POST | `/api/db/reauth` | `{ "password", "totp_code"? }` | `{ "token", "expires_at" }` (60 s) |
| POST | `/api/db/backups` | `{ "include_attachments": bool }` | `202 { "id", "status": "running" }` |
| GET | `/api/db/backups` | `?limit=` | Lista con `id`, `created_at`, `engine`, `schema_version`, `size_bytes`, `verified_at`, `attachments_included` |
| GET | `/api/db/backups/{id}/download` | — | Archivo con `Content-Disposition: attachment`, `Content-Type: application/gzip`, `Cache-Control: no-store` |
| POST | `/api/db/backups/{id}/verify` | — | `{ "valid", "tables": [{ "name", "rows", "ok" }] }` |
| DELETE | `/api/db/backups/{id}` | — | `204` |
| PUT | `/api/db/backups/schedule` | `{ "enabled", "interval_secs", "retention_copies" }` | Configuración efectiva |
| POST | `/api/db/restore` | multipart: archivo(s) + `{ "confirm_engine", "backup_attachments": bool }` | `202 { "id", "status": "running" }` |
| POST | `/api/db/migration/preflight` | `{ "target_url", "include_attachments" }` | `{ "ok", "checks": [{ "name", "ok", "detail" }], "estimate": { "rows", "seconds" } }` |
| POST | `/api/db/migration` | `{ "target_url", "preflight_id" }` | `202 { "id", "status": "maintenance" }` |
| GET | `/api/db/migration/{id}` | — | `{ "state", "progress": { "table", "rows_copied", "rows_total" }, "error"? }` |
| POST | `/api/db/migration/{id}/rollback` | — | `202`; descarta el destino y sale de mantenimiento |

`target_url` se valida y **nunca** se devuelve en una respuesta ni se registra en auditoría (solo host y motor).

### 4.3 Estado de la migración

```
preflight → ready → maintenance → snapshot → copying → verifying → cutover → completed
                                        ↘ failed ↗        ↘ rolled_back
```

- El estado vive en `system_info` (`db_migration_state`) para sobrevivir a un reinicio; al arrancar con un estado incompleto se informa en la consola y **no** se reanuda solo.
- Un solo trabajo de respaldo o migración a la vez; el segundo recibe `409 db.job_in_progress`.
- Progreso por sondeo (`GET …/{id}` cada 1 s); sin SSE en F8.

### 4.4 Errores

| Código | HTTP | Cuándo |
|---|---:|---|
| `db.not_admin` | 403 | Rol distinto de `admin`. |
| `db.reauth_required` / `db.reauth_failed` | 403 | Falta el token de reautenticación o expiró / contraseña o código 2FA incorrectos. |
| `db.job_in_progress` | 409 | Ya hay un respaldo, restauración o migración en curso. |
| `db.backup_invalid_signature` | 422 | Firma o `archive_sha256` no verifican. |
| `db.backup_schema_newer` | 422 | `schema_version` del archivo mayor que la del binario. |
| `db.backup_format_unsupported` | 422 | `format` desconocido. |
| `db.backup_table_mismatch` | 422 | Tablas del manifiesto ≠ esquema del binario. |
| `db.restore_target_not_empty` | 409 | Restauración sobre una base con datos y sin `confirm_engine` correcto. |
| `db.migration_preflight_failed` | 422 | Destino inaccesible, no vacío, versión incompatible o sin espacio. |
| `db.migration_cutover_failed` | 500 | No se pudo escribir el TOML; el servicio sigue en el origen y sale de mantenimiento. |
| `db.storage_full` | 507 | Sin espacio al escribir el archivo o el esquema temporal. |

## 5. Modo mantenimiento

- Se activa solo durante `maintenance → cutover` de una migración.
- **Escrituras** (`POST`/`PUT`/`PATCH`/`DELETE`) → `503` con `Retry-After: 30` y `{ "error": "db.maintenance" }`.
- **Lecturas** (`GET`) permitidas, incluida la consola, para poder observar el progreso.
- Excepciones: `/healthz`, `/api/auth/login|logout|me`, `/api/db/*` (solo `admin`).
- La ingestión de auditoría también recibe `503` (no se exceptúa: la cadena no debe crecer mientras se copia). Los emisores deben reintentar o encolar; F8-01 lo verifica y F8-07 lo garantiza.
- Los latidos de dispositivo (`POST /api/devices/heartbeat`) reciben `503`; tras el periodo de gracia (60 s por defecto) los equipos aparecen `offline`. Es esperado y se documenta en la guía; no afecta a las sesiones remotas activas, que no dependen del control plane.
- Al salir de mantenimiento se restablece el servicio sin reinicio; el **corte** sí exige reinicio (`requires_restart: true`).

## 6. Auditoría

Categoría `db` (nueva variante en `audit-core`), `source: api`, `actor` = usuario administrador, `subject_type: backup` o `migration`:

| Acción | `details` permitidos | Prohibidos |
|---|---|---|
| `db.backup_created` | `backup_id`, `engine`, `schema_version`, `rows_total`, `size_bytes`, `attachments_included` | contenido de filas, rutas absolutas, secretos |
| `db.backup_verified` | `backup_id`, `valid`, `tables` (solo nombres y conteos) | contenido |
| `db.backup_downloaded` | `backup_id`, `ip` | URL firmada, token |
| `db.backup_deleted` | `backup_id`, `reason` | ruta absoluta |
| `db.restore_started` / `_completed` / `_failed` | `backup_id`, `engine`, `schema_version`, `error_code` | contenido, contraseña, `target_url` |
| `db.migration_preflight` | `source_engine`, `target_engine`, `checks` (nombres y resultado) | `target_url`, credenciales |
| `db.migration_started` / `_verified` / `_completed` / `_failed` / `_rollback` | `migration_id`, motores, conteos, `error_code` | contenido, credenciales |
| `db.reauth_denied` | `reason` | — |

Regla Zero Secrets vigente: ni contraseñas, ni cadenas de conexión, ni claves, ni contenido de chat en `details`, logs ni notificaciones.

## 7. Programación y retención

- `CERCANO_BACKUPS_DIR` (por defecto `./data/backups`, permisos `0700`), `CERCANO_BACKUP_INTERVAL_SECS` (86400) y `CERCANO_BACKUP_RETENTION_COPIES` (30).
- El trabajo periódico corre en el mismo proceso (patrón del bucle de checkpoints); la primera copia automática ocurre un intervalo después del arranque, para no competir con el inicio.
- Retención por número de copias: se borran las más antiguas **verificadas**, nunca la más reciente ni la única verificada. Borrar deja evento.
- Nombres: `cercano-backup-<UTC ISO básico>.jsonl.gz` y `cercano-attachments-<misma marca>.tar.gz`; un nombre con rutas o caracteres fuera de `[A-Za-z0-9._-]` se rechaza.

## 8. Seguridad

- Directorio `0700`, archivos `0600`, escritura atómica; descarga solo autenticada y auditada.
- Sin claves privadas en el archivo (ADR-011 §2.9). La consola muestra un aviso permanente: el respaldo de claves es un procedimiento aparte.
- El archivo contiene mensajes de chat en claro (igual que la BD): se trata como material sensible, se cifra al salir del equipo y no se sube a repositorios ni a almacenamiento público.
- Límite de tamaño por archivo (por defecto 2 GiB) y comprobación de espacio libre antes de escribir.
- Un respaldo descargado no habilita sesiones: no contiene tokens válidos por diseño (las sesiones caducan y el archivo se verifica, no se reproduce en caliente).
